# 합성 시스템 설계 문서

**작성일:** 2026-02  
**목적:** 돌 합성(Synthesis) 기능의 요구사항·로직·매칭 규칙 정의

---

## 1. 기본 플로우

- **유저 입력:** 보유 원소 비율 + 온도 조건 + 압력 조건
- **시스템:** 비율로 유사 광물 매칭 → 온도·압력으로 다형질 구분 → 한계 원소 기준으로 배치 크기 산정 → 합성 실행
- **결과:** IMA 등록 광물 1종으로 돌 생성 (stones INSERT)

---

## 2. 비율 기반 매칭 (레시피 선택 방식 아님)

유저는 **4000개 이상의 광물 레시피 중에서 하나를 고르지 않는다.**

- 유저가 가진 원소(인벤토리)의 **비율**을 그대로 합성에 사용
- 서버가 `mineral_recipes` 중 **유사한 elements 비율**을 가진 광물을 찾아 매칭
- 매칭 기준: 정규화된 비율 거리(예: L1, 코사인)로 가장 가까운 광물 선택

### 2.1 데이터 접근: 로컬 레시피 + DB 검증

비율 매칭·PM 필터·사전 검증을 매 입력마다 DB 조회하면 부담이 크다.

- **로컬(클라이언트 또는 캐시)**: `mineral_recipes` 전체를 한 번 로드. 비율 거리·PM 필터·fallback·사전 검증·예상 결과 표시는 모두 **로컬에서** 처리.
- **DB**: 합성 실행 시에만 사용. 서버가 검증(보유량, recipe_id, 비율, 온도·압력) 후 `stones` INSERT 등만 수행.

슬라이더/온도·압력 변경 시 DB 호출 없음. 합성 버튼 눌렀을 때만 RPC 호출.

---

## 3. 다형질 처리: 온도·압력 독립 설정

같은 원소 비율을 가진 광물이 여러 종 있을 수 있다 (다형질, polymorph).  
예: SiO₂ → 석영(Quartz) / Tridymite / Cristobalite

### 3.1 유저 설정

**온도(Temperature)** · **압력(Pressure)** 을 **독립적으로** 설정한다.

온도는 **5단계**로 세분화하여 PM-형태 연계와 habit 다양성을 반영한다.

| 축 | 옵션 | 설명 |
|----|------|------|
| 온도 | 1 / 2 / 3 / 4 / 5 | 온도 레벨 (1=급냉 방향, 5=서냉 방향) |
| 압력 | 저압 / 고압 | 상압~천부 / 심부~맨틀 |

조합: 5×2 = 10가지

### 3.2 PM 매핑

유저가 선택한 온도·압력 조합 → 해당하는 PM 번호 집합으로 매핑.

같은 비율 후보들 중 `pm_ids`가 해당 PM 집합과 **겹치는** 광물만 필터 → 그 중 1종 선택 (gacha_weight 가중 랜덤 등).

| 조합 | 대표 PM 예 | 비고 |
|------|------------|------|
| 1·저압 | 22, 23, 25, 47, 48, 50, 54, 55, 56, 57 | 수화·퇴적·증발 |
| 1·고압 | 거의 없음 (fallback: 저압) | |
| 2·저압 | 22, 23, 25, 48, 50, 54, 55, 56, 57 | 저온 수성 변질 |
| 2·고압 | fallback: 저압 | |
| 3·저압 | 12, 14, 15, 33, 45, 46 | 열수·온천·해저열수 |
| 3·고압 | 32 일부 | |
| 4·저압 | 7, 8, 9, 19, 20, 34, 35, 36, 51 | 화성·페그마타이트 |
| 4·고압 | 32, 38, 39, 40, 41, 43 | 변성·맨틀 |
| 5·저압 | 7, 8, 9, 19, 20 | 마그마·용암 |
| 5·고압 | 32, 38, 39, 40, 41 | 고온 변성 |

상세 PM 목록은 `docs/PM_DISTRIBUTION.md` 참고.

### 3.3 PM 필터 fallback (PM 세트 확대)

비율 매칭 후보는 있으나 PM 필터에서 **겹치는 광물이 0개**일 수 있다. 이 경우 **PM 세트를 확대**하여 재검색한다.

- 인접 온도·압력 조합의 PM을 합쳐서 더 넓은 PM 세트로 재검색
- 그래도 후보가 없으면 추가 확대 또는 최종 fallback(PM 무시) — 구현 시 상세 정의
- 결과: **원소만 갖추면** 비율·온도·압력과 관계없이 대부분 합성 성공. 동소체가 있는 조성은 각 PM 구간을 커버하므로 fallback 호출이 드물다.
- 부가 효과: 드문 조건에서 특이한 결정(희귀 variant) 생성 가능

## 4. 유사 비율 처리

### 4.1 세 가지 케이스

| 상황 | 처리 |
|------|------|
| **필수 원소 누락** | 합성 실패 (**유일한 실패 사유**) |
| **비율이 허용 오차 이내** | 100% 크기로 생성 |
| **비율이 비슷하지만 오차 초과** | 한계 원소(limiting reagent) 기준으로 비례 축소 |

PM 필터 fallback(3.3) 덕분에 원소만 갖추면 웬만한 경우 합성 가능.

### 4.2 필수 원소 누락

매칭된 광물의 `elements`에 포함된 **모든 원소**를 유저가 보유해야 한다.

- 유저가 원소 X를 전혀 보유하지 않는데, 매칭 광물이 X를 필요로 하면 → **합성 실패**
- 예: O가 0인데 SiO₂ 매칭 → 실패

### 4.3 오차 허용 (100% 크기)

비율이 “충분히 가까우면” 완전 일치로 간주하여 100% 크기로 생성.

- 정규화된 원소 비율의 차이(L1 거리 또는 코사인 유사도)가 **임계값 ε 이내**이면 100% 처리
- 예: ε = 0.05 (5%) → 소수점 오차·반올림 등으로 99.x% 되는 것을 방지

### 4.4 한계 원소(limiting reagent) 기반 축소

비율이 다르지만 모든 필수 원소가 있는 경우:

1. 매칭된 광물의 비율 `r_el` (각 원소당 계수)로 1회분 필요량 계산
2. 1회분 총량 = 300 (PRD 고정)
3. 유저 보유량 `u_el` 기준 **가능한 최대 배치 수**:
   ```
   batches = min(u_el / needed_el)  for all elements
   ```
4. **실제 소비량** = `needed_el * batches` (각 원소별)
5. **생성되는 돌의 초기 크기** = `batches` 비율 (1.0 = 100%, 0.5 = 50%)

**예시:**

- 매칭: SiO₂ (Si:O = 1:2)
- 1회분(300): Si 100, O 200
- 유저 보유: Si 100, O 100
- batches = min(100/100, 100/200) = 0.5
- 결과: Si 50, O 100 소비 → **50% 크기**의 석영 생성

### 4.5 과잉 원소

매칭 광물에 없는 원소는 사용하지 않는다. 필요한 원소만 차감하고, 나머지는 인벤토리에 유지.

## 7. RPC 입출력 (초안)

### 입력

```json
{
  "elements_ratio": { "Fe": 2, "O": 3 },
  "temperature": 4,
  "pressure": "low",
  "batch_count": 1
}
```

- `elements_ratio`: 유저 보유 원소 비율 (0인 원소 제외)
- `temperature`: 1~5 (정수, 온도 레벨)
- `pressure`: `"low"` | `"high"`
- `batch_count`: 합성 횟수 (1 이상, 기본 1)

### 출력 (성공)

```json
{
  "status": "success",
  "stone_id": 123,
  "recipe_id": 45,
  "mineral_name": "Hematite",
  "batch_factor": 1.0,
  "elements_consumed": { "Fe": 120, "O": 180 }
}
```

### 출력 (실패)

```json
{
  "status": "error",
  "code": "MISSING_ELEMENT",
  "message": "필요한 원소가 부족합니다."
}
```

## 8. 합성 UI 설계

### 8.1 플로우

1. **주기율표에서 합성할 원소 선택** (클릭으로 선택/해제, **누른 순서대로** 리스트 추가)
2. **선택된 원소 나열** (별도 패널에 칩/리스트로 표시, 순서 유지)
3. **비율 조절** (원소당 슬라이더 1개 + 정수 입력)
4. **온도·압력 선택**
5. **합성 실행**

보유량 기준으로만 선택하면 Si, O, H 등 흔한 원소만 쌓여 반복 합성이 되므로, **유저가 의도적으로 원소를 고르고 비율을 설정**하는 방식으로 설계한다.

**사전 검증:** 합성 버튼을 누르기 **전에** 비율·온도·압력·보유량을 검증한다. 합성 불가(필수 원소 누락 등)인 경우 **버튼 비활성화** 또는 안내 표시. 유저가 클릭 후 실패를 경험하지 않도록 한다.

### 8.2 선택 순서

- 주기율표에서 클릭한 **순서대로** 조절 리스트에 추가된다.
- 순서를 아무렇게나 두면 안 되고, **누른 순서가 리스트 순서**가 된다.
- 리스트에서 위 → 아래 = 첫 번째 선택 → 마지막 선택.

### 8.3 비율 조절: 원소당 슬라이더 1개 + 정수 입력

- **원소당 슬라이더 1개**: 2원소면 2개, 3원소면 3개.
- **정수 계수 입력**: Si 1, O 2 → 1:2 화학식 비율로 정확히 지정.
- **동기화**: 한쪽 변경 시 다른 쪽도 함께 갱신.

슬라이더를 연속 값으로 두면 33.33%, 66.67% 같은 소수가 되어 정확한 정수 비를 맞출 수 없다. 따라서 **슬라이더는 이산 눈금**으로만 동작한다.

### 8.4 슬라이더 조절 규칙: 아래가 위에 영향 없음

- 리스트 **맨 위 원소** = 첫 번째 선택한 원소.
- **맨 아래 슬라이더**를 움직이면 → **맨 위 원소 비율은 변하지 않음**.
- 맨 아래 슬라이더 변경 시, 나머지(맨 위 제외) 원소들끼리만 비율을 재분배한다.

예: A(위) · B(중간) · C(아래)  
→ C 슬라이더 조절 시: C 변함, B가 나머지를 받아 변함, **A는 고정**.

### 8.5 슬라이더 눈금: LCM 기반

- **눈금 수** = 현재 선택된 원소들로 구성된 광물들의 비율 합(denominator) **최소공배수(LCM)**.
- 예: Si:O 1:2(합 3), 2:3(합 5) → LCM(3, 5) = 15 → 슬라이더 16칸 (0~15).
- 데이터에 존재하는 모든 광물 비율을 **정확히** 선택 가능.
- **적용 범위**: **현재 선택된 원소들만** 포함하는 광물만 대상으로 LCM 계산.

### 8.6 슬라이더 동작

- **스냅**: 눈금 위치에만 멈춤 (이산 값만 허용).
- **눈금 간격에 따른 동작**: 눈금 간격이 **작을 때**(눈금 수가 많을 때, LCM 큼) — 드래그 중에는 **자유 슬라이드**, 릴리즈 시에만 가장 가까운 유효 비율로 스냅. 렉 같은 끊김 방지. 눈금 간격이 **클 때**는 드래그 중에도 스냅 OK.
- **표시**: 내부는 정수 비, UI에는 **백분율**로 표시 (예: Si 33.3%, O 66.7%).
- **LCM 상한**: 계산값이 비정상적으로 클 때만(수억 이상 등) 상한 적용. 수천~수만은 그대로 처리.

## 9. 미량 원소 (불순물·발색소)

PRD: 미량 원소는 광물 종을 바꾸지 않고 **색상(발색)** 만 변경한다.

### 9.1 발색소–광물 관계

같은 발색소라도 **광물마다 발색 결과가 다르다.**

| 발색소 | 광물 | 결과 색 |
|--------|------|---------|
| Cr | 강옥(Corundum) | 루비 (빨강) |
| Cr | 녹주석(Beryl) | 에메랄드 (녹색) |
| Fe | 석영(Quartz) | 자수정(보라) / 시트린(노랑) |
| Fe | 강옥 | 황색 사파이어 |
| Ti | 강옥 | 청색 사파이어 |

결정 구조(리간드장)에 따라 전이 금속의 d 전자 전이가 달라져 색이 달라진다.

### 9.2 채택 방안: 결정계 그룹 × 전이 금속 매트릭스

**외부 habit DB·색상 매핑 DB는 사용하지 않는다.**  
IMA 결정계 데이터 + 유저 설정 환경(온도/압력) + 미량 원소 + 고유 시드(Seed)만으로, 수학적 연산으로 색상과 형태를 실시간 절차 생성한다.

**전이 금속 8종 × 결정계 3그룹 → Target Hue 매트릭스 (코드 내 하드코딩 테이블):**

| 미량 원소 | 그룹 1: 등축/정방 | 그룹 2: 육방/삼방 | 그룹 3: 사방/단사/삼사 |
|-----------|-------------------|-------------------|------------------------|
| Cr | 진홍색 (Deep Red) | 붉은색(삼방) / 녹색(육방) | 연두색 (Light Green) |
| Fe | 노란색~갈색 | 보라색/파란색 | 붉은 갈색 |
| Cu | 청록색 (Cyan) | 파란색 (Azure) | 짙은 녹색 (Malachite Green) |
| Mn | 연분홍색 | 적자색 (Rhodonite Red) | 짙은 붉은색 |
| Co | 파란색 (Cobalt Blue) | 선홍색 (Vivid Pink) | 짙은 보라색 |
| V | 황록색 | 에메랄드 그린 | 회녹색 |
| Ti | 무색~옅은 노랑 | 짙은 파란색 | 짙은 갈색 |
| Ni | 사과 녹색 | 연한 녹색 | 노란빛 녹색 |

- **투입량** (`amount_level`) → 명도/채도 제어 (농도 소광: 고농도 시 명도 감소)
- **일반 원소**(Ca, Na, K, C 등): 색상(Hue)은 베이스 광물 기본색 유지. 투명도(Alpha) 감소, 클라우드/크랙 노이즈 증가

### 9.3 결정계 3그룹 분류 이유

**과학적 근거 (결정장 이론):**  
전이 금속 이온의 색은 배위 구조(coordination geometry)에 따라 달라진다. 결정계 대칭이 배위 다면체의 형태를 결정하므로, 유사 대칭을 가진 결정계끼리 묶는다.

| 그룹 | 결정계 | 배위 대칭 | 특성 |
|------|--------|-----------|------|
| 그룹 1 | 등축, 정방 | 높은 대칭 (정팔면체·정사면체) | 규칙적 배위장 |
| 그룹 2 | 육방, 삼방 | 6·3축 대칭 | 삼각/육각 배위, 방향성 있음 |
| 그룹 3 | 사방, 단사, 삼사 | 낮은 대칭 | 뒤틀린 배위 다면체 |

**실용적 이유:** 3그룹 × 8원소 = 24개 hue 값으로 매트릭스 관리가 단순하고, 7개 결정계 각각 매핑 시 복잡도·데이터 부담 증가.

### 9.4 발색소 추가량·강도

- **기준:** 1회분 총량 300당 trace 원소 개수 (1≈0.33%, 2≈0.67%, 3≈1%)
- **유저 선택:** 발색소 추가 시 **1개 / 2개 / 3개 중 하나를 유저가 선택**
- **강도 구간:**
  - 1개 선택 → **약한 발색** 구간 내에서 랜덤
  - 2개 선택 → **중간 발색** 구간 내에서 랜덤
  - 3개 선택 → **강한 발색** 구간 내에서 랜덤
- 선택한 개수가 구간을 정하고, 그 구간 안에서 세부 강도는 랜덤 적용

## 10. 절차 생성 시드

합성된 돌은 **고유 시드**를 가져야 하며, 같은 시드로 렌더링 시 항상 동일한 형태가 나와야 한다.

### 10.1 저장 및 DNA 구조

- **위치:** `stones.dna` (JSONB)
- **생성 시점:** 합성 RPC에서 `stones` INSERT 시 서버가 1회 생성
- **시드 형식:** int64 (예: PostgreSQL `floor(random() * 2^63)::bigint`)

클라이언트는 서버로부터 극히 가벼운 DNA JSON만 전달받아 절차적으로 3D 돌을 렌더링한다.

```json
{
  "stone_id": 12345,
  "mineral_name": "Quartz",
  "dna": {
    "seed": 847291047582,
    "crystal_system": "trigonal",
    "environment": {
      "temperature": 1,
      "pressure": "high"
    },
    "trace_elements": [
      { "element": "Fe", "amount_level": 2 },
      { "element": "Ca", "amount_level": 1 }
    ]
  }
}
```

### 10.2 Godot RNG 변경 위험

- 엔진 버전 업데이트 시 `RandomNumberGenerator` 알고리즘이 바뀔 수 있음
- 동일 시드라도 다른 버전에서 다른 형태가 나올 수 있음

### 10.3 대응: 자체 PRNG 구현

- **직접 PRNG 구현** (예: PCG, xorshift128+ 등 고정 알고리즘)
- 절차 생성에서 Godot 내장 RNG 대신 이 PRNG만 사용
- 같은 시드 → 같은 수열 → 같은 렌더링 결과 보장

**필수 조건:**
1. PRNG 알고리즘 고정 (변경 시 버전 관리)
2. 절차 생성에서 `rand()` 호출 순서 고정
3. 시드 외 다른 랜덤 소스(시스템 시간 등) 사용 금지

## 11. 렌더링 파이프라인 (절차 생성)

외부 형태 DB(Habit) 및 방대한 색상 매핑 DB를 사용하지 않는다. **IMA 결정계 + 유저 설정(온도/압력) + 미량 원소 + 시드**만으로 수학적 연산으로 형태와 색상을 실시간 절차 생성한다.

### 11.1 환경 기반 절차적 형태 생성

성장 축과 환경 변수의 수학적 상호작용으로 우연하고 불규칙한 형태를 도출한다.

**1단계: 성장 축(Axes) 세팅**  
IMA `crystal_system` 기반 3D 공간 뼈대 설정:

| 결정계 | 축 구성 |
|--------|---------|
| 등축/정방/사방 | 직교 X, Y, Z (90도) |
| 육방/삼방 | 60°/120° 평면 축 + 수직 축 |
| 단사/삼사 | 비대칭 각도 기울어진 축 |

**2단계: 시드에 의한 비대칭 성장**  
- 모든 면이 동일하게 자라지 않음  
- Seed 난수로 각 방향 초기 성장 속도(Growth Rate)에 편차 부여  
- 결과: 한쪽 축만 뻗거나, 특정 면이 파이게 되어 우연히 십자가·별·하트 모양 등 자연 생성 (파레이돌리아 유도)

**3단계: 환경 변수 모디파이어**

| 변수 | 영향 | Low | High |
|------|------|-----|------|
| **온도** | habit (축별 성장 비율) | 급냉 → 성장 편차 극대화. 뾰족(Acicular)·수지상(Dendritic) 확률 ↑ | 서냉 → 고른 성장. 다면체(Euhedral)·블록 확률 ↑ |
| **압력** | 표면 질감만 (habit 무관) | 매끄러운 표면 (정동/빈 공간) | 3D 노이즈(Voronoi/Perlin) ↑, 모서리 뭉개짐, 덩어리(Massive) |

*압력: 실제로는 정형/비정형에 영향이 있으나, 설계상 표면 질감으로만 단순화.*

**4단계: PM별 habit 가중치 (확률 보정)**

PM에 따라 habit을 **차단하지 않고 가중치만 조정**한다. 드문 조합도 낮은 확률로 나올 수 있다.

| PM 유형 (온도 레벨) | 선호 habit | 비선호 habit |
|---------------------|------------|--------------|
| 1-2 (퇴적·수화) | 바늘·수지상·편상 | 등립·블록 |
| 3 (열수) | 기둥·판상·바늘 | 극단 수지상 |
| 4-5 (화성·페그마타이트) | 등립·블록·기둥 | 수지상 |
| 고압 (변성) | 덩어리(압력이 표면 노이즈로 반영) | — |

구현: habit 템플릿(판상/기둥/등립/바늘 등 5~10종)의 축 비율 + 시드 노이즈. PM별로 habit 선택 확률에 승수 적용.

**조정 포인트:**
- 시드→성장률: 균등 분포 vs 편향 분포(베타 등) 또는 템플릿 선택 + 노이즈
- 온도: 각 레벨별 성장 편차 배율 (1=극대, 5=최소)
- PM 가중치: habit별 승수 테이블 (예: 페그마타이트 PM → 등립×2, 바늘×0.3)

### 11.2 미량 원소 발색

섹션 9.2의 결정계 그룹 × 전이 금속 매트릭스로 Target Hue 도출. `amount_level`로 채도·명도 제어. 비발색소(Ca, Na 등)는 투명도·불순물 효과만 적용.

## 12. 구현 순서 제안

1. 온도·압력 → PM 매핑 테이블 정의
2. 비율 거리 함수 + 유사 광물 검색 로직
3. `synthesize_stone` RPC (트랜잭션, 검증 포함)
4. LabUI 합성 탭 (원소 선택·비율 조절·온도·압력·실행)
5. 미량 원소 UI + 결정계 그룹 × 전이 금속 매트릭스
6. 자체 PRNG 구현 + 절차 생성에 시드 적용
7. 렌더링 파이프라인 (환경 기반 형태 생성 + 발색 알고리즘)
